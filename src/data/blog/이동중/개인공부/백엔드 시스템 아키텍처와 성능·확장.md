## 1. 전체 아키텍처

대규모 백엔드 시스템은 클라이언트의 요청을 받아
애플리케이션에서 처리하고, 데이터를 저장하거나 조회한 뒤
응답을 반환하는 구조로 동작한다.

```text
Client
  ↓
DNS / CDN / WAF
  ↓
Load Balancer
  ↓
┌───────────────────────────────────┐
│       Application Layer           │
│                                   │
│  Spring A   Spring B   Spring C   │
│                                   │
│  Tomcat                           │
│    ↓                              │
│  DispatcherServlet                │
│    ↓                              │
│  Controller → Service             │
│    ↓                              │
│  Repository → JPA → JDBC          │
│    ↓                              │
│  HikariCP                         │
└───────────────────────────────────┘
  ↓
┌───────────────────────────────────┐
│            Data Layer             │
│                                   │
│  RDBMS      Redis       Kafka     │
│  영속성      캐시        이벤트    │
└───────────────────────────────────┘
```

각 계층은 서로 다른 책임을 갖는다.

- 네트워크 계층: 요청 전달, 부하 분산, 보안
- 애플리케이션 계층: 비즈니스 로직 실행
- 데이터 계층: 데이터 저장, 조회, 정합성 관리
- 비동기 처리 계층: 이벤트 전달, 후속 작업 처리
- 운영 계층: 배포, 확장, 장애 대응, 모니터링

## 2. Spring Boot 내부 요청 처리

일반적인 Spring MVC의 요청 처리 흐름은 다음과 같다.

```text
HTTP Request
    ↓
Tomcat
    ↓
Servlet Filter
    ↓
DispatcherServlet
    ↓
HandlerInterceptor
    ↓
Controller
    ↓
Service
    ↓
Repository
    ↓
JPA / Hibernate
    ↓
JDBC
    ↓
HikariCP
    ↓
Database
```

### Tomcat

Tomcat은 HTTP 서버이자 Servlet Container다.

- HTTP 연결 처리
- 요청 처리 스레드 관리
- Servlet 실행
- HTTP 응답 반환

### DispatcherServlet

Spring MVC의 중앙 요청 처리기다.

HandlerMapping과 HandlerAdapter 등을 활용해
요청에 적절한 Controller 메서드를 실행한다.

### IoC / DI

Spring Container가 객체를 생성하고 의존성을 주입한다.

### AOP

트랜잭션, 로깅 등 공통 관심사를
비즈니스 로직과 분리해 적용한다.

### JPA / Hibernate

엔티티의 영속성을 관리하고
SQL 생성 및 실행을 지원한다.

### HikariCP

DB 커넥션을 재사용해
연결 생성 및 종료에 따른 비용을 줄인다.

## 3. Tomcat 스레드와 DB 커넥션

Tomcat 스레드와 HikariCP 커넥션은 서로 다른 자원이다.

| 구분 | Tomcat Thread | HikariCP Connection |
|---|---|---|
| 역할 | HTTP 요청 처리 | DB와 통신 |
| 관리 주체 | Tomcat | HikariCP |
| 제한 | 스레드 풀 | 커넥션 풀 |
| 대표 병목 | 요청 처리 스레드 고갈 | 커넥션 획득 대기 |

예를 들어 다음과 같은 환경을 가정하자.

```text
Tomcat 최대 스레드 = 200
HikariCP 최대 커넥션 = 10
동시 HTTP 요청 = 100
```

모든 요청이 동시에 커넥션을 요구한다면:

```text
100개 Tomcat 스레드
        ↓
     HikariCP
        ├── 10개: DB 커넥션 사용
        └── 90개: 커넥션 획득 대기
```

일반적인 Spring MVC + JDBC 환경에서는
커넥션을 기다리는 스레드가 블로킹될 수 있다.

따라서 커넥션 풀 부족이
Tomcat 스레드 고갈로 이어질 수 있다.

### HikariCP 주요 메트릭

| 메트릭 | 의미 |
|---|---|
| Active | 현재 사용 중인 커넥션 |
| Idle | 사용 가능한 커넥션 |
| Pending | 커넥션을 기다리는 스레드 |
| Acquire | 커넥션 획득 소요 시간 |
| Usage | 커넥션 점유 시간 |
| Timeout | 커넥션 획득 타임아웃 |

Active가 최대치이고 Pending이 지속적으로 증가한다면
커넥션 풀 병목을 의심할 수 있다.

다만 근본 원인은 느린 SQL, 긴 트랜잭션,
락 경합 등일 수 있으므로 함께 확인해야 한다.

## 4. TPS, Latency, Concurrency

### TPS

Transactions Per Second.

초당 완료한 트랜잭션 수다.

### RPS

Requests Per Second.

초당 처리한 HTTP 요청 수다.

HTTP 요청 하나가 DB 트랜잭션 하나와
항상 일치하는 것은 아니다.

### Latency

요청 하나를 완료하는 데 걸리는 시간.

### Concurrency

동시에 진행 중인 작업 수.

예를 들어:

```text
DB 커넥션 = 10
커넥션 점유 시간 = 100ms
```

각 커넥션이 100ms마다 한 작업을 완료한다면:

```text
TPS = 10 × (1000 / 100)
    = 100 TPS
```

이는 다른 병목이 없고 커넥션을
연속적으로 사용하는 경우의 이론적인 처리량이다.

### Little's Law

안정적인 시스템의 장기 평균에서:

L = λ × W

- L: 평균 동시 작업 수
- λ: 단위 시간당 처리량
- W: 평균 체류 시간

예를 들어:

```text
처리량 = 100 RPS
평균 응답 시간 = 0.2초

평균 동시 요청 = 100 × 0.2
              = 20
```

응답 시간이 1초로 증가하고 처리량이 유지된다면
평균 동시 요청 수는 100이 된다.

Little's Law는 작업 수, 처리량, 체류 시간 사이의
관계를 나타내며 병목의 원인을 직접 알려주지는 않는다.

## 5. 성능 병목과 장애 전파

DB가 느려졌을 때 다음과 같은 현상이 발생할 수 있다.

```text
SQL 실행 지연
    ↓
커넥션 점유 시간 증가
    ↓
HikariCP Active 증가
    ↓
HikariCP Pending 증가
    ↓
Tomcat 스레드 대기 증가
    ↓
HTTP 응답 지연
    ↓
타임아웃 및 오류 발생
```

따라서 애플리케이션 CPU 사용률이 낮아도
서비스가 느려질 수 있다.

스레드들이 CPU 연산 대신
DB나 외부 I/O를 기다리고 있을 수 있기 때문이다.

성능 분석에서는 다음을 함께 확인한다.

- CPU / Memory / GC
- Tomcat Thread
- HikariCP Active / Pending / Usage
- SQL 실행 시간과 실행 계획
- DB Lock / I/O
- HTTP p95 / p99
- Distributed Tracing

## 6. Scale-up과 Scale-out

### Scale-up

한 서버의 자원을 늘리는 방식.

```text
8 Core / 32GB
      ↓
32 Core / 128GB
```

장점:

- 상대적으로 단순한 구조
- 서버 간 통신 비용이 적음
- 분산 데이터 관리 부담이 적음

단점:

- 물리적 확장 한계
- 고사양 하드웨어 프리미엄
- 단일 서버 장애 위험

### Scale-out

서버 수를 증가시키는 방식.

```text
Load Balancer
   ├── Server A
   ├── Server B
   └── Server C
```

장점:

- 수평 확장
- 탄력적인 자원 관리
- 장애 대응 및 다중화

단점:

- 네트워크 통신 증가
- 분산 상태 관리
- 운영 복잡도 증가

### Scale-up이 더 비쌀 수 있는 이유

고성능 하드웨어는 CPU, 메모리 대역폭,
전력, 냉각, 메인보드 등의 요구사항이 높아진다.

따라서 성능 증가분에 비해
하드웨어 가격이 비선형적으로 증가할 수 있다.

다만 Scale-out 역시 네트워크, 로드밸런싱,
복제, 운영 비용을 추가로 요구한다.

Scale-up이 항상 비싼 것은 아니다.

### Amdahl's Law

병렬화 가능한 작업 비율이 P이고
병렬 처리 자원 수가 N이라면:

S(N) = 1 / ((1-P) + P/N)

순차적으로 실행해야 하는 작업이 존재하므로
자원을 추가해도 성능이 무한히 증가하지 않는다.

## 7. 고가용성과 장애 대응

### Load Balancing

여러 서버에 요청을 분산한다.

### Failover

장애 서버에서 정상 서버로 처리를 전환한다.

### Auto Scaling

부하와 정책에 따라 서버 수를 조정한다.

### RTO

Recovery Time Objective.

장애 후 서비스 복구에 허용되는 시간.

### RPO

Recovery Point Objective.

장애 시 허용 가능한 데이터 손실 범위.

### 핵심 고려사항

- 서버 다중화
- Health Check
- Graceful Shutdown
- 상태 및 세션 외부화
- Retry와 멱등성
- DB 고가용성
- 장애 감지 및 자동 복구
- 모니터링과 알림

서버를 여러 대로 운영하더라도
DB가 한 대뿐이라면 DB는 단일 장애점이 될 수 있다.

## 핵심 정리

대규모 백엔드의 성능은
애플리케이션 서버의 사양만으로 결정되지 않는다.

HTTP 스레드, DB 커넥션, DB CPU, I/O 등
각 계층의 자원이 연결되어 있다.

따라서 전체 요청 흐름을 이해하고
병목과 장애 전파 경로를 분석해야 한다.
