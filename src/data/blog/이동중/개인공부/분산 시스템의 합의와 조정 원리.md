# 분산 시스템의 합의와 조정 원리

## 1. 분산 시스템의 근본적인 문제

서버 여러 대는 각각 독립적인 CPU, 메모리, 디스크를 가진다.

따라서 다른 서버의 상태를 알기 위해서는
네트워크 메시지를 주고받아야 한다.

그러나 네트워크에서는 다음 문제가 발생한다.

- 메시지 지연
- 메시지 손실
- 네트워크 분리
- 부분 장애
- 서버 간 상태 불일치

예를 들어 A가 B에게 메시지를 보냈는데
응답이 없다고 하자.

A는 B가 종료되었는지,
네트워크가 끊겼는지,
B에서 GC Pause가 발생했는지
즉시 확실하게 구분할 수 없다.

이것이 분산 시스템에서 합의가 어려운 이유다.

---

## 2. Consensus와 Raft

Consensus는 여러 서버가
하나의 결정에 합의하는 문제다.

Raft는 리더 기반으로 복제 로그에 합의하는 알고리즘이다.

```text
                Client
                   ↓
               Leader A
               /      \
              ↓        ↓
        Follower B  Follower C
```

Raft는 동일한 초기 상태에서
동일한 명령을 동일한 순서로 적용하는
State Machine Replication을 구현할 수 있게 한다.

### 서버 상태

- Leader: 로그 복제와 커밋 조정
- Follower: Leader의 메시지 수신
- Candidate: Leader 선거에 참여

### 주요 상태 정보

- currentTerm
- votedFor
- log[]
- commitIndex
- lastApplied

Leader는 nextIndex와 matchIndex도 관리한다.

## 3. Leader Election

Follower는 Leader의 Heartbeat를 기다린다.

일정 시간 동안 유효한 메시지를 받지 못하면
Election Timeout이 발생한다.

예를 들어 A가 먼저 타임아웃되었다고 하자.

```text
A:
1. Term 증가
2. Candidate 전환
3. 자기 자신에게 투표
4. RequestVote RPC 전송
```

RequestVote는 다음 정보를 전달한다.

```text
RequestVote(
    term,
    candidateId,
    lastLogIndex,
    lastLogTerm
)
```

Follower는 다음을 확인한다.

1. 후보의 Term이 유효한가?
2. 현재 Term에서 이미 투표했는가?
3. 후보의 로그가 충분히 최신인가?

3대 클러스터에서 2표 이상을 얻으면
Leader로 선출될 수 있다.

---

## 4. Term과 Heartbeat

Term은 선거 임기를 나타내는 논리적 번호다.

```text
Term 1 → Leader A
Term 2 → Leader B
Term 3 → Leader C
```

서버가 더 높은 Term을 관찰하면
자신의 Term을 갱신하고 Follower로 전환한다.

Leader는 Follower에게 주기적으로 Heartbeat를 보낸다.

Raft에서 Heartbeat는
entries가 비어 있는 AppendEntries RPC다.

Heartbeat는 Follower의 선거 타이머를
초기화하는 역할을 한다.

---

## 5. Log Replication

클라이언트가 다음 명령을 요청한다고 하자.

```text
SET balance = 50000
```

Leader는 자신의 로그에 명령을 추가한다.

```text
Index | Term | Command
------+------|---------------------
1     | 1    | SET balance = 50000
```

이후 Follower에게 AppendEntries를 보낸다.

```text
AppendEntries(
    term,
    leaderId,
    prevLogIndex,
    prevLogTerm,
    entries,
    leaderCommit
)
```

### AppendEntries의 역할

- Leader의 Term 전달
- 이전 로그 일치 여부 검증
- 새로운 로그 복제
- 충돌 로그 정리
- Commit Index 전달
- Heartbeat 수행

Follower는 로그 일치 여부를 검사한 후
성공 또는 실패를 응답한다.

Leader는 필요하면 복제 위치를 조정하여
Follower의 로그를 자신의 로그와 동기화한다.

## 6. Commit과 Quorum

3대 클러스터의 과반수는 2대다.

```text
A: [Index 1, Term 1]
B: [Index 1, Term 1]
C: []
```

현재 Term에 생성된 로그가 A와 B에 복제되었다면
Leader는 이를 커밋할 수 있다.

Raft에서 다음 세 개념은 구분해야 한다.

- Append: 로컬 로그에 기록
- Commit: 합의 규칙에 따라 확정
- Apply: State Machine에 적용

모든 Follower의 적용이 끝나야
Leader가 커밋하는 것은 아니다.

### Quorum

Majority = floor(N / 2) + 1

| 서버 수 | 과반수 | 장애 허용 수 |
|---|---|---|
| 3 | 2 | 1 |
| 5 | 3 | 2 |
| 7 | 4 | 3 |

과반수 집합 두 개는 반드시 겹친다.

이 성질과 로그 최신성 검사,
Term 및 커밋 규칙이 결합되어
커밋된 로그의 안전성을 보장한다.

---

## 7. Leader 장애와 로그 복구

```text
A: Index 1 존재 / 장애
B: Index 1 존재
C: 로그 없음
```

Index 1이 이미 커밋된 로그라면
새 Leader에게도 보존되어야 한다.

B는 C보다 최신 로그를 가지고 있으므로
선거 과정에서 유리하다.

B가 Leader가 되면
C에 누락된 로그를 복제할 수 있다.

반대로 A에만 존재했던 미커밋 로그는
장애 이후 새로운 Leader의 로그와 충돌하면
삭제되거나 덮어써질 수 있다.

Raft가 보장하는 것은
한번 커밋된 로그의 안전성이다.

---

## 8. Network Partition과 Split-Brain

```text
네트워크 그룹 1: A

네트워크 그룹 2: B, C
```

A는 자신이 기존 Leader라고 생각할 수 있지만
과반수를 확보할 수 없으므로
새로운 로그를 커밋하지 못한다.

B와 C는 과반수를 구성할 수 있어
새 Leader를 선출할 수 있다.

네트워크가 복구되면 A는
더 높은 Term을 확인하고 Follower로 전환한다.

### Split-Brain

서로 분리된 서버들이
충돌하는 리더 권한을 행사하는 문제다.

Raft는 과반수 커밋 규칙으로
서로 충돌하는 로그의 확정을 방지한다.

## 9. CAP Theorem과 일관성 모델

CAP는 네트워크 분리 상황에서
강한 일관성과 모든 정상 노드의 가용성을
동시에 보장할 수 없다는 정리다.

### Consistency

CAP에서의 Consistency는
Linearizability를 의미한다.

### Availability

정상 노드가 받은 요청에
최종적으로 응답을 반환하는 성질이다.

### Partition Tolerance

네트워크 분리 상황을 고려하는 성질이다.

### 일관성 모델

#### Linearizability

모든 작업이 실제 시간 순서를 보존하는
하나의 순서로 실행된 것처럼 보인다.

#### Sequential Consistency

모든 작업이 하나의 순서로 실행된 것처럼 보이고,
각 프로세스의 작업 순서를 유지한다.

서로 다른 프로세스 간 실제 시간 순서는
반드시 보존하지 않는다.

#### Eventual Consistency

새로운 변경이 멈추고 복제가 정상적으로 진행되면
복제본들이 결국 같은 상태로 수렴한다.

Raft를 사용하더라도 모든 로컬 읽기가
자동으로 Linearizable한 것은 아니다.

최신 읽기 보장을 위해 ReadIndex 같은
별도의 프로토콜이 필요할 수 있다.

## 10. 분산 락, Lease와 Fencing Token

여러 서버에서 동일한 작업을
중복 실행하지 않게 조정해야 하는 경우가 있다.

예를 들어 Redis에서 다음과 같이
락을 획득할 수 있다.

```redis
SET settlement:123 worker-A NX PX 10000
```

- NX: 키가 없는 경우에만 저장
- PX: 만료 시간 설정
- worker-A: 소유자 토큰

### Lease 문제

```text
00초: Worker A 락 획득
03초: Worker A GC Pause
10초: 락 만료
11초: Worker B 락 획득
12초: Worker A 재개
```

Worker A가 락 만료를 모르고
작업을 계속할 수 있다.

### Fencing Token

락 획득마다 단조 증가하는 번호를 발급한다.

```text
Worker A: Token 41
Worker B: Token 42
```

작업 대상 시스템은 더 최신 토큰을 승인한 이후
오래된 토큰의 쓰기를 거부한다.

단, 작업 대상이 토큰을
원자적으로 검증해야 효과가 있다.

### 멱등성

분산 락과 멱등성은 다른 문제를 해결한다.

- 분산 락: 동시 작업 실행 조정
- 멱등성: 중복 요청으로 인한 중복 효과 방지

실제 결제·정산 시스템에서는
트랜잭션, 락, 멱등성을 함께 고려해야 한다.

## 11. 실제 활용 기술

### etcd와 Kubernetes

Kubernetes는 클러스터의 원하는 상태를
etcd에 저장한다.

```text
kubectl
   ↓
Kubernetes API Server
   ↓
etcd (Raft)
   ↓
Kubernetes Controller
   ↓
Pod 상태 조정
```

etcd는 Raft 기반 합의를 사용해
클러스터 상태를 일관되게 관리한다.

etcd가 Pod를 직접 실행하는 것은 아니다.

Controller와 Scheduler, kubelet 등이
실제 상태를 조정한다.

### Kafka KRaft

KRaft는 Kafka 클러스터의 메타데이터를
Raft 기반 쿼럼으로 관리한다.

```text
KRaft Controller Quorum
       ↓
Kafka Brokers
       ↓
Topic Partitions
```

주의할 점은 KRaft의 메타데이터 합의와
Kafka 일반 메시지 파티션의 복제는
동일한 메커니즘이 아니라는 것이다.

Kafka 데이터 파티션에서는
ISR, High Watermark, ACK 등의 개념이 중요하다.

### ZooKeeper와 ZAB

ZooKeeper는 분산 조정 시스템이며
ZAB(ZooKeeper Atomic Broadcast) 계열 프로토콜을 사용한다.

Raft와 ZAB는 리더 기반 복제라는 공통점이 있지만
서로 다른 알고리즘이다.

과거 Kafka는 ZooKeeper를 활용했지만
KRaft를 통해 메타데이터 관리를
Kafka 자체의 컨트롤러 쿼럼으로 이전했다.

## 12. RPC와 REST

### RPC

Remote Procedure Call.

원격 서버의 기능을 호출하는 통신 모델이다.

```java
follower.appendEntries(
    term,
    prevLogIndex,
    entries
);
```

실제로는 네트워크 메시지를 통해
상대 서버에서 작업을 수행하도록 요청한다.

### REST

Representational State Transfer.

리소스와 통일된 인터페이스를 중심으로
설계하는 아키텍처 스타일이다.

```http
POST /raft/log-entries
Content-Type: application/json

{
  "term": 3,
  "entries": []
}
```

### 핵심 차이

| RPC | REST |
|---|---|
| 원격 기능 호출 중심 | 리소스 중심 |
| 메서드와 인자 | URI와 표준 HTTP 메서드 |
| gRPC, JSON-RPC 등 | HTTP REST API |

RPC도 데이터를 수정할 수 있고
REST API도 내부적으로 함수를 실행한다.

따라서 차이는 무엇을 최종적으로 수정하느냐가 아니라
외부에 제공하는 인터페이스의 설계 방식에 있다.

Raft의 AppendEntries는 로그 리소스를 변경할 수 있지만
분산 합의 프로토콜의 특정 동작을 호출하는 형태이므로
RPC라는 표현을 사용한다.

HTTP로 RPC를 구현할 수도 있으며,
HTTP를 사용한다고 자동으로 REST가 되는 것은 아니다.

## 핵심 정리

분산 시스템의 핵심 문제는
서버 간 상태 불일치와 네트워크 장애다.

Raft는 리더 선거, 로그 복제, 과반수 커밋을 통해
복제 로그의 안전성을 보장한다.

CAP는 네트워크 분리 상황에서
강한 일관성과 가용성 사이의 제약을 설명한다.

분산 락과 Lease, Fencing Token은
여러 서버의 작업 소유권을 조정하는 데 활용된다.

etcd, Kafka KRaft, ZooKeeper는
이러한 분산 합의 및 조정 원리를
서로 다른 방식과 목적으로 활용한다.
