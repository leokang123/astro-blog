## 1. DB의 전체 처리 구조

SQL이 실행되면 DB는 단순히 데이터를 읽고 쓰는 것이 아니라
실행 계획, 메모리, 락, 트랜잭션, 로그 등을 함께 관리한다.

```text
SQL Request
    ↓
Parser
    ↓
Optimizer / Query Planner
    ↓
Execution Engine
    ↓
Storage Engine
    ├── Buffer Pool
    ├── Index
    ├── Transaction / Lock / MVCC
    └── WAL / Redo / Undo
    ↓
Data Files
```

DBMS마다 내부 구조와 명칭은 다를 수 있다.

---

## 2. Transaction과 ACID

트랜잭션은 여러 DB 작업을
하나의 논리적인 작업 단위로 묶는 것이다.

예를 들어 계좌 이체는 출금과 입금이 함께 성공해야 한다.

```sql
BEGIN;

UPDATE account
SET balance = balance - 50000
WHERE id = 'A';

UPDATE account
SET balance = balance + 50000
WHERE id = 'B';

COMMIT;
```

중간에 실패하면 ROLLBACK할 수 있다.

### ACID

| 속성 | 의미 |
|---|---|
| Atomicity | 전부 실행되거나 전부 취소 |
| Consistency | 트랜잭션 전후 데이터 제약 유지 |
| Isolation | 동시 트랜잭션 간 간섭 제어 |
| Durability | 커밋된 변경의 내구성 |

실제 금융 이체에서는 잔액 검증,
거래 원장, 중복 요청 방지 등도 고려해야 한다.

---

## 3. 동시성 제어와 MVCC

동시에 여러 트랜잭션이 같은 데이터를 읽거나 수정하면
Lost Update, Dirty Read 등의 문제가 발생할 수 있다.

### Lock

충돌하는 데이터 접근을 제어한다.

- Shared Lock
- Exclusive Lock
- Row Lock
- Table Lock

### MVCC

Multi-Version Concurrency Control.

여러 버전의 데이터를 이용해
트랜잭션 간 읽기와 쓰기를 조정하는 기술이다.

예를 들어:

```text
Transaction A: 이전 버전 조회
Transaction B: 새로운 버전 생성
```

DBMS와 격리 수준에 따라
각 트랜잭션이 관찰하는 버전이 달라진다.

MVCC가 있다고 해서
모든 동시성 문제가 자동으로 해결되지는 않는다.

업무 규칙에 따라 비관적 락, 낙관적 락,
조건부 UPDATE 등이 필요할 수 있다.

### Isolation Level

- READ UNCOMMITTED
- READ COMMITTED
- REPEATABLE READ
- SERIALIZABLE

구체적인 동작은 DBMS마다 차이가 있다.

## 4. Buffer Pool과 Dirty Page

DB는 디스크 접근을 줄이기 위해
데이터 페이지를 메모리에 보관한다.

```text
SQL UPDATE
    ↓
Buffer Pool에서 페이지 수정
    ↓
Dirty Page 생성
    ↓
나중에 데이터 파일에 기록
```

Dirty Page는 메모리에서 변경되었지만
아직 데이터 파일에 기록되지 않은 페이지다.

문제는 디스크에 기록하기 전에
서버가 종료되면 변경 내용이 사라질 수 있다는 것이다.

이를 해결하기 위해 WAL이 사용된다.

---

## 5. WAL과 Redo Log

### WAL (Write-Ahead Logging)

데이터 페이지를 디스크에 쓰기 전에
복구에 필요한 로그를 먼저 영속화하는 원칙이다.

```text
UPDATE
   ↓
메모리 데이터 변경 / 로그 생성
   ↓
WAL 영속화
   ↓
COMMIT 완료
   ↓
나중에 데이터 페이지 기록
```

실제 메모리 변경과 로그 생성,
디스크 영속화 시점은 DBMS와 설정에 따라 다르다.

### Redo Log

장애 복구 시 변경 사항을
다시 적용하기 위한 로그다.

대표적인 구현:

- PostgreSQL: WAL
- MySQL InnoDB: Redo Log
- Oracle: Redo Log

WAL은 기록 순서에 관한 원칙이고,
Redo Log는 변경 재적용이라는 목적을 강조한다.

### 장애 복구 예시

```text
초기 잔액: 100,000원

UPDATE → 50,000원

Buffer Pool: 50,000원
Data File: 100,000원
WAL: 변경 기록 영속화
```

이 상태에서 서버가 종료되어도
로그가 안전하게 보존되어 있다면
DB 재시작 시 변경을 복구할 수 있다.

실제 로그는 단순한 SQL 문자열이 아니라
페이지 변경 정보 등 복구 데이터를 포함한다.

---

## 6. Undo Log

Undo Log는 변경 이전 상태를 관리하여
롤백과 MVCC 등에 활용된다.

| 구분 | 주요 역할 |
|---|---|
| Redo | 변경 사항 재적용 |
| Undo | 변경 전 상태 복원 |
| WAL | 로그 선기록 원칙 |

MySQL InnoDB의 Undo Log는
롤백과 이전 버전 조회에 사용된다.

PostgreSQL은 별도의 Undo Log 중심이 아니라
테이블의 행 버전 등을 이용해 MVCC를 구현한다.

## 7. Replication

Replication은 데이터를 다른 DB 서버에도 유지하는 기술이다.

```text
        Primary
        /     \
       ↓       ↓
   Replica A  Replica B
```

대표적인 목적:

- 고가용성
- 읽기 부하 분산
- 재해 복구

PostgreSQL 물리적 스트리밍 복제는
WAL 기록을 Replica에 전달해 재생한다.

MySQL의 일반적인 복제는 Binlog를 활용한다.

### 비동기 복제

```text
1. Primary에서 UPDATE 실행
2. Primary COMMIT
3. 클라이언트에 성공 응답
4. Replica로 변경 전파
```

Replica에 변경이 반영되기 전에
Primary가 장애를 일으키면
커밋된 일부 데이터가 손실될 수 있다.

### 동기 복제

정해진 Replica의 확인을
커밋 조건에 포함하는 방식이다.

내구성 측면에서 유리할 수 있지만,
네트워크 지연과 Replica 장애가
쓰기 응답 시간 및 가용성에 영향을 줄 수 있다.
---

## 8. Replication과 Raft의 차이

| 비교 | 일반적인 비동기 DB 복제 | Raft |
|---|---|---|
| 목적 | 데이터 복제 | 복제 로그 합의 |
| 쓰기 확정 | Primary 단독 가능 | 현재 Term 로그의 과반수 복제 |
| 장애 시 | 복제 지연에 따른 손실 가능 | 커밋 로그 보존 |
| 리더 전환 | 별도 장애 전환 체계 | Leader Election 포함 |
| 네트워크 분리 | 구성에 따라 동작 차이 | 과반수 없이는 새 로그 커밋 불가 |

Replication은 데이터를 복제한다는 넓은 개념이다.

Raft는 여러 서버가 로그의 순서와 커밋에
합의하도록 만드는 특정 알고리즘이다.

따라서 Replication이 반드시 Raft를 의미하지는 않는다.

---

## 핵심 정리

DB는 트랜잭션과 동시성 제어를 통해
데이터 정합성을 관리한다.

Buffer Pool은 디스크 I/O를 줄이고,
WAL과 Redo Log는 장애 복구를 지원한다.

Replication은 데이터를 다른 서버에도 유지하지만,
복제 방식에 따라 데이터 손실 가능성과 일관성 수준이 달라진다.
