# 프로세스와 스레드 — 질문으로 익히기

질문을 읽고 먼저 소리 내어 답해 보세요. 처음에는 30초 정도로 핵심을 설명하면 충분합니다. 답변 상자의 짧은 문장은 면접에서 말할 예시이고, 그 아래 문단은 이유를 이해하기 위한 설명입니다. 짧은 답변이 낯설면 해설부터 읽고 다시 자기 말로 답해 보세요. 답변을 확인할 때는 문장을 그대로 외우기보다, 내가 빠뜨린 이유나 조건이 무엇인지 살펴보세요.

앞부분은 기본 개념을 설명하는 연습이고, 뒷부분은 익숙한 설명이 어디까지 성립하는지 따져 보는 질문입니다.

## 기본을 자기 말로 설명하기

### 1. 프로세스와 스레드는 어떻게 다른가요?

‘프로세스는 무겁고 스레드는 가볍다’는 표현 없이 설명해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 프로세스는 실행 중인 프로그램 하나로, 주소 공간과 실행에 필요한 자원을 가집니다. 스레드는 그 안의 실행 흐름입니다. 같은 프로세스의 스레드는 자원을 공유하지만, 각자의 실행 위치와 레지스터 상태를 유지합니다.

사진 변환 프로그램을 실행하면 사용할 메모리와 열린 파일 등을 관리하는 프로세스가 생깁니다. 그 안에서 한 스레드는 사진 A를 읽고, 다른 스레드는 사진 B를 변환할 수 있습니다. 두 스레드가 같은 메모리를 이용하면서도 다른 일을 진행하는 것입니다. 주소 공간은 프로그램이 코드와 데이터를 주소로 찾아 쓰는 범위이고, 레지스터는 CPU가 계산 중인 값을 담는 작은 저장 공간입니다.

두 개념을 나누는 핵심은 자원과 실행입니다. 같은 프로그램을 실행해도 프로세스가 다르면 작업 상태가 다를 수 있고, 같은 프로세스 안에서도 스레드마다 다른 부분을 실행할 수 있습니다.

**“그렇다면 하나의 프로세스에 스레드가 여러 개 있어야만 하나요?”** 하나의 실행 흐름으로 동작하는 프로세스도 있습니다. 프로세스가 자원과 주소 공간의 경계를 제공한다는 점은 그대로입니다.

</details>

### 2. 같은 프로세스의 스레드는 무엇을 공유하나요?

함수 호출을 진행하는 데 필요한 정보까지 생각해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 같은 주소 공간을 사용하므로 코드, 전역 데이터, 힙을 공유합니다. POSIX에서는 열린 파일 디스크립터도 공유합니다. 반면 실행 위치와 레지스터 문맥, 함수 호출 상태를 유지할 스택은 각각 필요합니다.

코드는 실행할 명령이고, 전역 데이터와 힙은 여러 함수에서 함께 쓸 데이터를 담습니다. 힙은 실행 중 메모리를 할당해 쓰는 영역입니다. 스택은 각 함수 호출의 지역 변수와 돌아갈 위치 등을 유지합니다. 파일 디스크립터는 열린 파일 등을 가리키는 정수 번호입니다. POSIX는 이런 기능의 공통 사용법을 정한 표준입니다.

두 스레드가 같은 함수를 호출하더라도 하나는 시작 부분, 다른 하나는 반환 직전에 있을 수 있습니다. 따라서 ‘같은 코드를 사용한다’는 것과 ‘같은 실행 상태를 가진다’는 것은 다릅니다. 스택만 따로 가진다고 답하면 PC와 레지스터 상태를 빠뜨리게 됩니다.

**“스택이 따로 있으면 다른 스레드의 접근도 막히나요?”** 스택의 위치가 다르다는 뜻이지 다른 스레드의 접근을 차단한다는 뜻은 아닙니다. 유효한 지역 변수의 주소를 안전하게 전달받으면 접근할 수 있습니다. 다만 그 변수가 사라진 뒤 사용하거나, 읽는 도중 다른 스레드가 값을 바꾸는 문제는 따로 막아야 합니다.

</details>

### 3. PCB는 왜 필요한가요?

저장되는 항목을 나열하기 전에, 이 정보가 없다면 무엇을 할 수 없는지 생각해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 운영체제는 실행을 중단한 뒤에도 프로세스를 관리하고 다시 이어 실행할 수 있어야 합니다. PCB는 식별자, 상태, 스케줄링과 자원 관련 정보 등을 관리하는 자료구조를 가리킵니다. 멀티스레드에서는 스레드별 실행 문맥도 필요합니다.

PCB는 Process Control Block의 약자입니다. 스케줄링은 누구에게 CPU를 줄지 정하는 일이고, 실행 문맥은 멈춘 계산을 이어가는 데 필요한 상태입니다.

예를 들어 이미지의 100번째 줄을 처리하던 스레드가 멈췄다면 실행 위치뿐 아니라 줄 번호와 계산 중인 값도 기억해야 합니다. 메모리에 코드와 데이터가 남아 있어도 ‘어디까지 실행했고 어떤 값을 계산 중이었는지’를 잃으면 그대로 이어갈 수 없습니다. 실제 OS에서는 이 정보가 여러 구조체와 커널 스택 등에 나뉠 수 있으므로 모든 정보를 하나의 고정된 PCB에 넣는다고 단정할 필요는 없습니다.

**“PC만 저장하면 되지 않나요?”** PC(Program Counter)는 실행 위치를 나타냅니다. 실행 위치가 같더라도 사용할 레지스터 값과 스택 위치가 다르면 다른 계산이 됩니다. 전체 힙을 매번 PCB에 복사하는 것도 아닙니다.

</details>

### 4. Ready와 Blocked는 어떻게 다른가요?

두 작업 모두 현재 CPU에서 실행 중이지 않은데, 왜 상태를 나눌까요?

<details>
<summary>답변과 해설 펼치기</summary>

> Ready는 실행할 수 있지만 CPU를 기다리는 상태이고, Blocked는 입력 도착 같은 조건이 충족되어야 진행할 수 있는 상태입니다. 대기 조건이 풀리면 실행 가능해지지만, 곧바로 CPU를 받는다고 보장되지는 않습니다.

파일을 읽으려는 A는 데이터가 아직 도착하지 않으면 Blocked입니다. 필요한 데이터가 도착하면 Ready가 되고, OS가 A에게 CPU를 배정하면 Running이 됩니다. 반면 필요한 데이터가 이미 준비된 B가 단지 실행 순서를 기다린다면 처음부터 Ready입니다. CPU가 비어도 입력이 아직 없는 A는 진행할 수 없습니다. ‘누구를 먼저 실행할까’를 결정하기 전에 ‘실행할 수 있는가’를 구분해야 하는 이유입니다.

**“Blocked 상태인 스레드의 우선순위를 높이면 실행되나요?”** 우선순위를 높인다고 필요한 이벤트가 발생하는 것은 아닙니다. 실행 가능 여부와 실행 순서는 별개의 문제입니다.

</details>

### 5. 문맥 교환에서는 어떤 일이 일어나나요?

이미지를 계산 중인 스레드 A를 멈추고 B를 실행했다가, 다시 A로 돌아오는 상황을 떠올려 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 현재 실행을 나중에 재개할 수 있도록 필요한 상태를 저장하고, 다음 실행 대상을 선택해 그 상태를 복원합니다. 대기가 필요하거나 선점되는 등의 상황에서 실행 대상이 바뀔 수 있습니다.

A가 중간 합계 30을 계산한 상태에서 멈췄다고 해 봅시다. CPU의 레지스터를 B가 사용하면 그 안의 값이 달라집니다. 따라서 OS는 A에게 필요한 값을 보관했다가, A의 차례가 왔을 때 다시 넣어 이어가게 해야 합니다. 이 과정이 저장과 복원입니다. 선점은 OS가 실행 중인 대상을 중단시키고 다른 대상에게 CPU를 주는 것을 말합니다. 같은 프로세스 안의 스레드라도 레지스터 상태와 실행 위치가 다르므로 문맥 교환이 필요합니다. 다른 프로세스로 넘어간다면 주소 공간 관련 처리도 고려합니다.

**“커널에 들어가기만 해도 문맥 교환인가요?”** 커널은 운영체제의 핵심 부분입니다. 같은 스레드 A가 운영체제 서비스를 받기 위해 커널 코드를 실행하는 것과, A 대신 B가 실행되는 것은 다릅니다. 뒤의 경우에 실행 주체가 바뀝니다.

</details>

### 6. 같은 프로세스의 스레드끼리 전환하면 비용이 없나요?

주소 공간이 그대로라는 사실이 무엇을 줄여 주고, 무엇까지 없애지는 못하는지 설명해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 주소 공간을 재사용할 수 있어도 실행 문맥의 저장·복원과 스케줄링 비용은 남습니다. 바뀐 작업의 메모리 접근에 따라 캐시의 유용성도 달라질 수 있습니다. 따라서 스레드 전환을 비용이 없는 작업이라고 볼 수는 없습니다.

캐시는 CPU 가까이에 데이터를 두어 빠르게 다시 쓰게 하는 저장 공간입니다. A가 사진 A를 처리하며 채운 캐시가 남아 있어도 B가 사진 B를 처리하면 필요한 데이터는 다를 수 있습니다. 그러면 새 데이터를 가져오는 비용이 듭니다. 같은 주소 공간을 쓴다는 이유만으로 계산 상태나 사용하는 데이터까지 같은 것은 아닙니다.

‘상대적으로 가볍다’는 설명을 ‘항상 일정한 배수만큼 빠르다’로 바꾸면 안 됩니다. 작업의 크기와 전환 이후의 메모리 접근, 하드웨어와 OS가 모두 영향을 줍니다.

**“문맥 교환마다 캐시 전체를 비우나요?”** 그렇게 단정할 수 없습니다. 캐시 내용이 남더라도 새 작업에 유용하지 않아 비용이 생기는 경우와, 실제 무효화 처리는 구분해야 합니다.

</details>

### 7. 멀티프로세스와 멀티스레드 중 무엇을 선택하겠나요?

공통 데이터를 자주 읽는 작업과, 실패를 격리하고 싶은 외부 변환 작업을 비교해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 데이터 공유가 잦으면 스레드가 편리할 수 있고, 독립 실행과 메모리 격리가 중요하면 프로세스 분리를 검토하겠습니다. 프로세스는 IPC와 자원 관리 비용을, 스레드는 공유 데이터의 동기화와 경합을 함께 고려해야 합니다.

예를 들어 여러 작업이 같은 이미지 설정을 자주 읽는다면 같은 메모리를 쓰는 스레드가 편리할 수 있습니다. 반면 오류가 잦은 변환 프로그램을 따로 실행하고 싶다면 프로세스를 나눠 메모리 오류의 영향을 줄일 수 있습니다. 대신 입력과 결과를 전달하는 프로세스 간 통신, 즉 IPC가 필요합니다.

스레드끼리 같은 데이터를 바꾸려 한다면 실행 순서를 조정하는 동기화가 필요합니다. 같은 자원을 얻으려고 서로 기다리는 상황이 경합입니다. 어느 한쪽을 고르는 것보다 선택의 이유가 중요합니다. 이 상황에서는 공유할 데이터의 크기·빈도, 실패가 미치는 범위, 작업 사이 의존성을 확인해야 합니다. 여러 프로세스 각각에 여러 스레드를 두는 혼합도 가능합니다.

**“프로세스를 나누면 공유 DB의 경쟁도 없어지나요?”** 주소 공간을 분리해도 공통 외부 자원을 갱신한다면 그 자원에 대한 조율은 필요합니다. 격리되는 경계를 정확히 설명해야 합니다.

</details>

### 8. 동시성과 병렬성은 어떻게 다른가요?

한 번에 하나의 실행 흐름만 실행할 수 있는 CPU를 기준으로도 설명해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 동시성은 여러 작업의 진행을 함께 다루는 것이고, 병렬성은 여러 계산이 실제로 동시에 실행되는 것입니다. 하나의 논리 CPU에서도 작업을 번갈아 진행할 수 있지만, 두 CPU 실행 흐름을 같은 순간에 실행하는 것은 아닙니다.

한 CPU에서 A를 조금 실행하고 B를 조금 실행하며 둘 다 진행시키는 것은 동시성의 예입니다. 서로 다른 CPU 실행 자원에서 A와 B의 계산을 같은 시각에 수행하면 병렬 실행입니다. 여기서 논리 CPU는 OS가 실행을 배정하는 CPU 단위입니다. 스레드의 개수와 실제로 동시에 실행할 수 있는 개수는 다릅니다. 스레드를 많이 만들었다는 사실만으로 병렬성을 얻었다고 볼 수 없습니다.

**“그렇다면 CPU가 하나일 때 여러 스레드는 쓸모없나요?”** 파일이나 네트워크의 입력을 기다리는 A가 잠든 동안 B가 계산하면 시간을 활용할 수 있습니다. 하지만 A와 B가 계속 계산만 한다면 CPU 하나의 계산 능력 자체가 늘어나는 것은 아닙니다.

</details>

### 9. fork, exec, wait는 각각 무엇을 하나요?

셸이 명령 하나를 실행하고 다시 입력을 받는 과정을 설명해 보세요. Linux/Unix 계열을 가정합니다.

<details>
<summary>답변과 해설 펼치기</summary>

> fork는 자식 프로세스를 만들고, exec는 현재 프로세스의 프로그램 이미지를 교체합니다. 부모는 wait 계열로 자식의 종료 결과를 기다리고 회수할 수 있습니다. exec 자체가 새 프로세스를 추가로 만드는 것은 아닙니다.

셸은 터미널 명령을 받아 실행하는 프로그램입니다. 사용자가 사진 변환 명령을 입력하면 셸이 fork로 자식을 만들고, 자식은 exec로 자신의 실행 코드와 메모리 구성을 사진 변환 프로그램의 것으로 바꿉니다. 사진 변환이 끝나면 부모 셸이 wait로 종료 결과를 확인할 수 있습니다. 여기서 부모·자식은 서로 다른 프로세스입니다. 부모는 종료 결과를 확인하고 다음 명령을 받을 수 있습니다. 생성·교체·회수가 나뉘어 있다는 점을 설명하면 됩니다.

**“종료한 자식이 좀비라면 CPU에서 무슨 일을 하나요?”** 이미 실행을 마쳤습니다. 기본적인 종료 처리에서 아직 회수되지 않은 최소 정보가 남은 상태입니다. 고아는 부모 관계에 대한 표현이므로 같은 개념이 아닙니다. 신호 처리 설정 등에 따라 좀비 처리에는 차이가 있습니다.

</details>

### 10. 프로세스끼리는 어떻게 데이터를 주고받나요?

IPC 이름 세 개를 말하는 데서 그치지 말고, 사용하는 쪽이 무엇을 설계해야 하는지 설명해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 파이프나 소켓으로 데이터를 전달하거나, 공유 메모리에 함께 접근할 수 있습니다. 파이프는 바이트 스트림이라 데이터 구분과 대기를 생각해야 합니다. 공유 메모리는 접근 순서와 수명 관리가 필요합니다. 통신 형태와 데이터 크기, 장애 처리 요구에 따라 선택하겠습니다.

파이프의 바이트 스트림은 데이터가 연속된 바이트로 흐른다는 뜻입니다. 사진 두 장을 연달아 보낸다면 수신자는 어디까지가 첫 사진인지 알아야 하므로, 사진 길이를 먼저 보내는 등의 약속이 필요합니다.

공유 메모리에서는 A가 사진 데이터를 쓰는 도중 B가 읽어 불완전한 사진을 얻지 않도록 순서를 맞춰야 합니다. 데이터를 보내거나 함께 볼 수 있다는 것만으로 ‘사진 한 장을 완성한 뒤 전달한다’는 규칙까지 자동으로 생기는 것은 아닙니다.

**“공유 메모리로 바꾸면 항상 빨라지나요?”** 동기화와 관리 비용도 포함해 비교해야 합니다. 수단 이름만으로 성능을 확정할 수 없습니다.

</details>

## 기본 설명에서 놓치기 쉬운 조건

### 11. 시스템 콜을 실행하면 반드시 다른 스레드로 바뀌나요?

여기서 문맥 교환은 CPU가 실행하는 주체가 바뀌는 것을 뜻합니다.

<details>
<summary>답변과 해설 펼치기</summary>

> 반드시 그렇지는 않습니다. 시스템 콜로 커널에 진입해도 같은 스레드가 서비스를 수행한 뒤 돌아올 수 있습니다. 대기가 필요하거나 선점되어 다른 실행 대상으로 넘어갈 때 문맥 교환이 발생할 수 있습니다.

시스템 콜은 파일 읽기처럼 OS 서비스를 요청하는 호출입니다. 사용자 모드는 일반 프로그램의 권한으로, 커널 모드는 OS가 자원을 관리할 수 있는 권한으로 실행하는 상태입니다.

A가 입력을 요청해 커널 코드를 실행하고 바로 결과를 받아 A로 돌아오면, 중간에 실행한 코드의 권한은 바뀌어도 다른 스레드 B로 넘어간 것은 아닙니다. 반대로 입력이 없어 A가 기다리는 동안 B를 실행했다면 실행 주체도 바뀝니다. 커널 진입 과정에서도 상태 저장이 나타날 수 있으므로, ‘레지스터를 저장했다’는 사실만으로 다른 스레드가 실행되었다고 판단하면 안 됩니다.

입력이 이미 준비된 경우에는 바로 처리할 수 있지만, 결과가 올 때까지 호출한 스레드를 기다리게 하는 블로킹 입력에서는, 아직 데이터가 없다면 기다려야 할 수 있습니다. 같은 종류의 요청이어도 진행 조건이 달라질 수 있다는 점까지 설명하면 좋습니다.

**더 생각해 보기:** “시스템 콜은 문맥 교환과 무관하다”는 반대 방향의 단정도 맞을까요? 대기와 선점 경로가 있다는 점 때문에 그것도 지나친 설명입니다.

</details>

### 12. 각자 스택을 가진다면 다른 스레드의 지역 변수에는 접근할 수 없나요?

일반적인 Linux/POSIX C 프로그램입니다. A가 함수 안에서 지역 변수 x를 만들고, 그 주소를 B에게 전달합니다. A의 함수는 아직 끝나지 않았고, B가 읽는 동안 A가 x를 바꾸지 않도록 순서를 맞췄습니다. 이 조건에서 B가 x를 읽을 수 있는지 설명해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 스택을 따로 유지한다는 것은 함수 호출 상태가 따로 있다는 뜻입니다. 같은 주소 공간 안에 있으므로 조건을 갖춰 전달받은 주소로 지역 객체에 접근할 수 있습니다. 다만 객체 수명과 충돌하는 접근에 대한 동기화는 별도로 지켜야 합니다.

B의 함수에서 A의 지역 변수 이름 x를 그대로 적어 쓸 수는 없습니다. 하지만 A가 전달한 주소를 통해 그 변수가 놓인 메모리에 접근할 수는 있습니다. 변수 이름을 사용할 수 있는 코드 범위와 메모리 접근 가능성은 다릅니다. 상대 함수의 지역 변수 이름을 직접 사용할 수 없어도 포인터로 가리킬 수 있습니다.

**“객체를 만든 함수가 먼저 반환하면요?”** 지역 객체의 수명이 끝난 뒤에는 유효한 접근으로 볼 수 없습니다. **“힙에 두면 해결되나요?”** 힙에 할당한 메모리는 그 함수를 빠져나갔다고 바로 사라지지는 않습니다. 하지만 A가 B보다 먼저 메모리를 해제하면 여전히 문제가 됩니다. B의 사용 완료를 확인한 뒤 해제하는 등의 약속이 필요합니다.

</details>

### 13. 논리 CPU가 하나인데 여러 스레드를 쓰면 유리할 수 있나요?

한 번에 스레드 하나만 CPU에서 실행할 수 있고, OS가 각 스레드에 실행 시간을 배정한다고 가정합니다. I/O는 파일이나 네트워크 등의 입출력을 말합니다.

<details>
<summary>답변과 해설 펼치기</summary>

> 가능합니다. 한 스레드가 I/O를 기다리는 동안 다른 실행 가능한 스레드가 일을 하면 대기를 활용할 수 있습니다. 하지만 순수 계산 작업을 나누어도 CPU 실행 용량이 늘지는 않고 전환 비용이 추가될 수 있습니다.

사진 한 장을 읽는 동안 이미 읽어 둔 다른 사진을 처리하는 장면을 생각해 보세요. 이득은 두 계산을 같은 순간에 수행해서가 아니라, 기다리는 시간에도 진행할 일이 있어서 생깁니다. 비동기 I/O 같은 다른 방법으로도 대기를 겹칠 수 있습니다.

**“모든 스레드가 같은 입력을 기다린다면요?”** 다른 실행 가능한 일이 없다면 개수만 늘려서는 도움이 되지 않습니다. ‘멀티스레드니까 빠르다’보다 무엇이 병목인지 설명하는 답변이 정확합니다.

</details>

### 14. 주소 공간이 분리된 프로세스들은 어떻게 메모리를 공유하나요?

두 프로세스가 POSIX 공유 메모리를 명시적으로 설정한 상황입니다.

<details>
<summary>답변과 해설 펼치기</summary>

> 공유 메모리 객체를 각각의 가상 주소 공간에 매핑하면 해당 영역의 내용을 공유할 수 있습니다. 주소 공간 전체가 하나가 되는 것은 아니며, 두 프로세스에서 매핑 주소가 같을 필요도 없습니다.

매핑은 프로그램이 보는 주소를 실제 저장 영역에 연결하는 일입니다. A는 자기 주소 1000부터, B는 자기 주소 5000부터 같은 공유 영역을 보도록 설정할 수 있습니다. 주소 숫자는 달라도 같은 저장 영역을 보므로 한쪽이 쓴 결과를 다른 쪽에서 읽을 수 있습니다. 이 숫자는 설명용 예시입니다. 공유되는 구간을 함께 사용하는 만큼 접근 순서와 동기화도 설계해야 합니다.

**“공유 영역 안에 A의 포인터를 넣으면 B가 그대로 사용할 수 있나요?”** 같은 숫자 주소가 B에서도 같은 위치를 뜻한다고 보장할 수 없습니다. 예를 들어 공유 영역에서 20바이트 뒤에 있는 데이터는 A에게 1020, B에게 5020에 있습니다. A의 주소 1020 대신 ‘시작에서 20바이트 뒤’라는 거리, 즉 오프셋 20을 전달하면 B는 자신의 시작 주소에 20을 더해 위치를 찾을 수 있습니다.

</details>

### 15. 한 스레드가 블로킹 I/O를 하면 다른 스레드도 멈추나요?

입력을 요청한 뒤 결과가 올 때까지 호출한 스레드가 기다리는 방식을 블로킹 I/O라고 합니다. OS가 스레드마다 따로 CPU를 배정할 수 있는 1:1 모델과, 사용자 수준의 여러 실행 흐름을 OS 스레드 하나에 올려 번갈아 실행하는 N:1 모델을 비교해 보세요. 후자에서는 그 OS 스레드 자체가 대기 상태에 들어간다고 가정합니다.

<details>
<summary>답변과 해설 펼치기</summary>

> 1:1에서는 한 스레드가 대기해도 다른 실행 가능한 스레드는 스케줄링될 수 있습니다. 반면 N:1의 유일한 커널 스레드가 블록되면 그 위의 사용자 스레드들을 진행시킬 실행 기반도 멈춥니다.

Linux의 NPTL 스레드 구현은 1:1 모델입니다. OS가 A와 B를 각각 실행 대상으로 알기 때문에 A를 대기시킨 뒤 B를 선택할 수 있습니다.

반면 N:1에서는 A와 B의 실행 순서를 프로그램 쪽 라이브러리가 고르고, 실제로 OS가 CPU에 올리는 대상은 K 하나입니다. A의 입력 요청 때문에 K가 잠들면 B를 선택할 라이브러리 코드도 실행되지 못합니다. ‘B라는 작업이 존재한다’는 사실만으로 OS가 B를 직접 실행할 수는 없습니다.

다만 언어의 실행을 지원하는 런타임이 입력을 요청한 뒤 다른 일을 진행하게 하거나, 입력 처리를 별도 스레드에게 맡겨 K 자체는 잠들지 않게 한다면 가정이 달라집니다. 실행 모델의 이름보다 OS 스레드가 실제로 멈추는지 확인해야 합니다. 1:1에서도 다른 스레드가 가진 락을 기다리는 등 별도의 의존성으로 진행이 막힐 수 있습니다.

**“N:1에서 A와 B를 빠르게 번갈아 실행하면 두 코어를 동시에 쓸 수 있나요?”** 이 모델에서 OS가 배치할 스레드는 K 하나입니다. 번갈아 실행하는 속도를 높여도 K가 두 코어에서 동시에 실행되는 것은 아닙니다.

</details>

### 16. fork로 독립적인 자식을 만들면 부모 메모리를 전부 즉시 복사하나요?

Linux에서 파일에 직접 연결되지 않은 일반적인 프로세스 전용 메모리를 생각해 보세요. 부모의 변수 값이 자식의 변경 때문에 함께 바뀌어서는 안 됩니다. 두 프로세스가 변경을 함께 보려고 따로 설정한 공유 메모리는 이 질문에서 제외합니다.

<details>
<summary>답변과 해설 펼치기</summary>

> Linux는 Copy-on-Write를 사용하므로 일반적인 사적 페이지를 처음부터 모두 복사하지 않습니다. 초기에는 물리 페이지를 공유할 수 있고, 쓰기가 필요할 때 독립된 내용을 유지하도록 처리합니다. 다만 프로세스 관리와 페이지 테이블 관련 비용까지 없어지는 것은 아닙니다.

페이지는 일정한 크기의 메모리 묶음입니다. 부모와 자식의 변수 x가 모두 10이라면, 읽기만 할 때는 같은 실제 페이지를 가리켜도 결과가 같습니다. 자식이 x를 20으로 바꾸려 할 때 필요한 복사와 주소 연결 변경을 하면, 부모는 계속 10을 보고 자식만 20을 볼 수 있습니다. COW는 이런 방식으로 쓰기가 필요할 때까지 복사를 미루는 원리입니다. 교육용 COW 모델에서는 공유 중인 페이지에 바로 쓰지 못하도록 보호합니다. 쓰기 시도가 걸리면 ‘이 접근은 OS 처리가 필요하다’는 페이지 폴트가 발생하고, 커널이 필요한 복사와 주소 연결 변경을 처리합니다. 이때 디스크 읽기가 반드시 필요한 것은 아닙니다.

**“자식이 곧바로 exec를 한다면 어떤 이점이 있나요?”** exec는 현재 실행할 코드와 메모리 구성을 새 프로그램의 것으로 바꿉니다. 자식이 곧 교체할 옛 내용을 미리 전부 복사하지 않아도 된다는 이점이 있습니다. 반대로 자식이 많은 페이지를 수정하면 미뤄 둔 복사가 필요해질 수 있습니다.

**“공유 메모리와 같은 기능인가요?”** 사적 COW 쓰기는 내용의 독립성을 유지하기 위한 것이고, 명시적 공유 매핑은 변경을 함께 보는 것이 목적입니다.

</details>

### 17. 작업 스레드가 남아 있는데 main이 반환하면 어떻게 되나요?

Linux에서 C/POSIX 스레드를 사용하는 프로그램입니다. main이 새 스레드에게 사진 변환 함수를 맡긴 뒤, 그 함수가 끝나기 전에 main의 마지막 줄에 도달해 반환한다고 해 봅시다. 다른 스레드가 계속 실행되는지 설명해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> main에서 반환하면 프로세스 종료로 이어져 다른 스레드도 종료됩니다. 작업 스레드의 시작 함수가 반환하는 것은 해당 스레드의 종료입니다. main에서 pthread_exit를 호출하면 다른 스레드가 계속 진행할 수 있고, 작업 완료를 기다리고 싶다면 join을 사용해 수명을 설계할 수 있습니다.

| 동작 | 의미 |
|---|---|
| main 반환 또는 어느 스레드에서든 exit 호출 | 프로세스 종료와 다른 스레드 종료 |
| 작업 스레드 시작 함수 반환 | 해당 스레드 종료 |
| pthread_exit | 호출 스레드 종료. 마지막 스레드라면 프로세스도 종료 |
| pthread_join | 대상의 종료를 기다림 |
| pthread_detach | 종료 시 관련 자원을 자동 회수하도록 설정 |

작업 스레드의 시작 함수는 새 스레드에게 실행하라고 지정한 함수입니다. 사진 변환 함수가 반환하면 그 작업 스레드가 끝납니다. 그러나 C 프로그램의 main 반환은 프로그램 전체 종료로 이어지므로 아직 변환 중인 다른 스레드도 끝납니다.

사진을 끝까지 변환한 뒤 프로그램을 종료하려면 main에서 그 작업 스레드에 join을 하고, join이 끝난 다음 반환하도록 만들 수 있습니다. join을 호출한 main은 기다리고, 변환 스레드는 자기 일을 계속합니다.

‘메인 스레드가 끝난다’는 표현만으로는 종료 방식이 모호합니다. detach도 프로세스 수명에서 독립한다는 의미는 아닙니다.

**“main이 지역 변수 주소를 넘긴 뒤 pthread_exit를 호출하면 안전한가요?”** 다른 스레드가 살아 있어도 main 스레드가 끝난 뒤 그 지역 변수를 계속 써도 된다는 보장은 없습니다. 주소 숫자를 가지고 있는 것과 그 주소의 객체가 여전히 유효한 것은 다릅니다. 실행 완료뿐 아니라 데이터의 수명까지 보장해야 합니다. 이 규칙을 다른 언어의 main이나 데몬 스레드에 그대로 적용해서는 안 됩니다.

</details>

## 선택의 근거까지 설명하기

방법의 이름을 나열한 뒤 한 걸음 더 나아가 보세요. 어떤 조건에서 그 방법을 선택하고, 무엇을 확인하면 선택을 바꿀지 설명하는 연습입니다.

### 18. 스레드 풀의 크기를 정할 때 무엇을 기준으로 삼겠나요?

스레드 풀은 여러 작업에 스레드를 재사용하는 구조입니다. 작업자는 실제 일을 맡는 스레드이고, 큐는 아직 맡기지 못한 작업의 대기열입니다. 사진 크기를 계산하는 작업과 서버의 응답을 기다리는 작업에서 풀의 스레드 수를 어떻게 정할지 설명해 보세요. OS가 각각 실행 시간을 배정하는 일반적인 스레드 풀을 가정합니다.

<details>
<summary>답변과 해설 펼치기</summary>

> 사용할 수 있는 CPU 자원, 작업의 대기 비중, 외부 자원의 동시 처리 한도를 먼저 확인하겠습니다. 이를 바탕으로 초기 크기를 정하고 처리량·응답시간·큐의 대기를 측정해 조정하겠습니다. 스레드 수만 늘려서 해결되는지는 병목에 따라 다릅니다.

계산 위주의 작업에서는 이미 CPU를 충분히 사용하고 있다면 작업자를 더 만들어도 계산 자원이 늘지 않습니다. 반면 작업자가 외부 응답을 기다리는 동안 다른 일을 진행할 수 있다면 더 많은 작업자가 유용할 수 있습니다. 이는 출발점이며, 언어 런타임의 병렬 실행 제한이나 컨테이너 CPU 할당도 확인해야 합니다.

예를 들어 DB에 동시에 보낼 수 있는 요청이 10개로 제한되어 있다고 해 봅시다. DB 요청만 수행하는 작업자를 100개로 늘려도 나머지는 연결을 기다릴 수 있습니다. 이 숫자는 원리를 설명하기 위한 가정입니다. 대기가 많다는 이유만으로 수를 계속 늘릴 수는 없습니다. DB 연결이나 외부 서비스가 처리할 수 있는 양이 제한되어 있다면 그 앞에 대기자만 늘어날 수 있습니다. 따라서 ‘CPU 개수의 몇 배’라는 고정 숫자보다 실제 작업과 자원 한도를 설명해야 합니다.

**“큐를 크게 잡으면 작업자를 적게 두어도 되나요?”** 큐는 들어온 작업을 보관할 뿐 처리 능력을 추가하지 않습니다. 밀려드는 작업을 잠시 흡수할 수 있지만 대기시간과 메모리 사용량이 커질 수 있습니다. 풀 크기와 함께 큐의 한도, 초과 요청을 거절하거나 유입을 늦추는 정책도 정해야 합니다.

같은 양의 요청을 보내며 풀 크기를 바꿔 봅니다. 초당 완료한 요청 수인 처리량, 요청 하나가 끝날 때까지 걸리는 응답시간, 큐에 쌓인 작업 수와 CPU 사용률을 비교하면 선택의 근거를 만들 수 있습니다. 이 비교는 측정 계획이며 특정 최적값이나 성능 개선을 보장하는 공식은 아닙니다.

</details>

### 19. 여러 스레드가 안전하게 동작하도록 만들려면 반드시 락을 써야 할까요?

여기서 안전하다는 것은 여러 스레드가 함께 실행되어도 프로그램이 지켜야 할 결과와 규칙이 깨지지 않는다는 뜻입니다. 락은 보호할 구간에 한 번에 하나만 들어오게 조정하는 수단입니다. 락 이외의 대안과, 그 방법으로도 해결되지 않는 상황을 설명해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 반드시 락을 직접 사용해야 하는 것은 아닙니다. 변경 가능한 상태를 스레드별로 분리하거나, 불변 데이터를 공유하거나, 필요한 범위에 맞는 원자적 연산을 사용할 수 있습니다. 다만 무엇을 하나의 일관된 작업으로 보장해야 하는지부터 정해야 합니다.

가장 먼저 생각할 것은 **여러 스레드가 같은 변경 가능한 상태를 건드릴 필요가 있는가**입니다. 각자 계산한 결과를 완료 후 안전하게 모을 수 있다면 중간 상태를 함께 수정할 필요가 줄어듭니다. 예를 들어 스레드마다 사진 처리 개수를 따로 세고, 모든 작업이 끝난 뒤 합치면 하나의 카운터를 동시에 갱신할 필요가 없습니다. 대신 아직 세고 있는 값을 합치지 않도록 작업 완료를 확인해야 합니다.

생성 후 바뀌지 않는 불변 객체도 선택지입니다. 읽는 동안 값이 바뀌지 않으므로 갱신 충돌을 피할 수 있습니다. 다만 객체를 다른 스레드에 안전하게 전달하는 방법과, 새 버전으로 교체하는 과정까지 자동으로 해결되는 것은 아닙니다.

Java의 원자적 변수처럼 단일 값의 갱신을 보장하는 도구도 있습니다. 여기서 중요한 것은 보장의 범위입니다. **“잔액 두 개를 각각 원자적 변수로 만들면 이체 전체도 원자적인가요?”** A 계좌와 B 계좌에 각각 100원이 있고 A에서 B로 10원을 보낸다고 해 봅시다. A를 90원으로 바꾼 뒤 B를 110원으로 바꾸기 전에는 합계가 잠깐 190원으로 보일 수 있습니다. 각 변경이 하나의 동작처럼 수행되어도 두 변경을 합친 이체 전체가 하나의 동작이 되는 것은 아닙니다.

여러 값 사이의 관계를 한 번에 지켜야 한다면 락으로 묶거나, 상태 전체를 하나의 단위로 교체하는 등 그 관계에 맞는 설계가 필요합니다. 따라서 락을 직접 사용하지 않는 설계에서도, 결과를 전달하는 순서와 여러 변경을 묶어 보장하는 범위는 따져야 합니다.

</details>

### 20. 스핀락은 언제 유리하고, 단점은 어떻게 줄일 수 있을까요?

스핀락은 잠금이 풀릴 때까지 실행하면서 반복 확인하는 방식입니다. 실행을 멈추고 깨워지기를 기다리는 방식과 비교해 설명해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 잠금이 곧 풀리고 보유자가 실제로 실행 중이라면, 잠들었다가 다시 실행되는 비용을 피하는 이점이 있을 수 있습니다. 하지만 대기 중에도 CPU를 소비하므로 보유 시간과 스케줄링 조건을 함께 봐야 합니다. 오래 기다릴 수 있다면 잠드는 방식이나 제한된 스핀 뒤 잠드는 방식을 검토하겠습니다.

여기서 잠든다는 말은 스레드를 종료한다는 뜻이 아니라, OS가 그 스레드에 CPU를 주지 않고 기다리게 한다는 뜻입니다. 잠금이 풀려 깨워지면 다시 실행 기회를 얻습니다. 임계 구역은 락으로 보호하는 코드 부분입니다.

락을 잡은 스레드가 다른 코어에서 짧은 작업을 마치는 중이라면 반복 확인으로 곧 진행할 가능성이 있습니다. 반면 그 스레드가 CPU에서 내려갔다면 기다리는 쪽이 아무리 돌아도 보유자가 다시 실행되기 전에는 풀리지 않습니다. 소스 코드상 임계 구역이 짧다는 사실만으로 실제 대기시간이 짧다고 볼 수 없는 이유입니다.

**“실행 가능한 CPU가 하나뿐이라면요?”** 대기자가 CPU를 쓰는 동안 보유자는 일을 마칠 수 없습니다. 선점형 스케줄러가 나중에 보유자를 실행시켜 진행할 수는 있지만, 회전하는 시간이 유용한 작업이 되지는 않습니다. 이를 모든 상황에서 반드시 교착한다고 설명하면 안 됩니다.

여기서 회전은 CPU가 잠금 상태를 계속 확인하는 것을 말합니다. 보완 방법으로는 일정 시간만 반복 확인한 뒤 잠드는 혼합 방식이 있습니다. 짧은 대기의 이점을 노릴 수 있지만, 얼마나 회전할지와 안전하게 잠들고 깨우는 절차가 필요합니다. 또는 공유 구간을 줄여 경합 자체를 줄일 수 있으나, 여러 데이터 사이의 일관성을 깨뜨리지 않아야 합니다.

Linux의 사용자 공간 스핀락은 일반적인 잠금 문제의 기본 해법으로 권장되지 않습니다. OS·실행 문맥에 따라 잠들 수 있는지도 다르므로, 커널의 특수한 상황을 일반 애플리케이션에 그대로 적용하지 않는 것이 중요합니다.

</details>

## 추가로 생각해볼 문제

이번에는 결과만 맞히기보다, 어떤 순서로 일이 벌어지는지 먼저 설명해 보세요. 처음 보는 용어는 해설에서 익혀도 됩니다. 중요한 것은 지문에 주어진 조건으로 판단을 만들어 내는 과정입니다.

### 21. CPU는 쉬고 있는데 스레드 풀의 작업은 왜 끝나지 않을까요?

사진 처리 서버에 일을 맡길 스레드가 딱 4개 있습니다. 사진 요청 A·B·C·D가 들어와 각 스레드가 하나씩 맡았습니다. 여기서 작업은 ‘사진 한 장 처리’라는 일이고, 작업자는 그 일을 실행하는 스레드입니다.

각 사진 처리 작업은 중간에 썸네일, 즉 작은 미리보기 사진이 필요해집니다. 그래서 다음과 같이 동작합니다.

1. 같은 스레드 풀의 대기열에 ‘이 사진의 썸네일 만들기’를 별도 작업으로 넣습니다.
2. 썸네일 결과가 나올 때까지 현재 사진 처리 작업은 기다립니다.
3. 결과를 받으면 나머지 처리를 끝내고, 그때 스레드가 다음 작업을 맡습니다.

여기서 사진 처리 작업을 **부모 작업**, 썸네일 작업을 **자식 작업**이라고 부릅니다. 부모·자식 프로세스를 생성한다는 뜻은 아닙니다. 기존 스레드들이 처리할 일의 목록에 새 일을 추가하는 것입니다.

네 사진 처리 작업이 모두 썸네일 결과를 기다리는 시점이 되었습니다. 기다리는 스레드는 잠들어 CPU를 쓰지 않지만, 맡은 작업을 끝내지 않았으므로 대기열의 다른 작업을 받지 않습니다. 풀은 스레드를 자동으로 추가하지 않으며, 썸네일 작업은 실행되기만 하면 다른 작업을 기다리지 않고 끝납니다.

이후 왜 진행이 막히는지 설명해 보세요. 스레드를 하나 더 두는 방법과, 작업을 나누는 방식을 바꾸는 방법은 어떤 차이가 있을까요?

<details>
<summary>답변과 해설 펼치기</summary>

> 네 스레드가 모두 사진 처리 작업을 맡은 채 썸네일을 기다립니다. 썸네일 작업은 시작할 스레드를 얻지 못합니다. 사진 처리가 끝나야 스레드가 비는데, 그 사진 처리는 썸네일이 끝나야 하므로 서로 기다리는 상황입니다.

문제의 시점을 표로 펼쳐 보면 누가 무엇을 기다리는지 드러납니다.

| 위치 | 맡은 일 또는 기다리는 일 |
|---|---|
| 스레드 1 | 사진 A 처리 중, A의 썸네일 결과 대기 |
| 스레드 2 | 사진 B 처리 중, B의 썸네일 결과 대기 |
| 스레드 3 | 사진 C 처리 중, C의 썸네일 결과 대기 |
| 스레드 4 | 사진 D 처리 중, D의 썸네일 결과 대기 |
| 대기열 | A·B·C·D의 썸네일 생성 작업이 시작을 기다림 |

**CPU가 비었다고 스레드가 맡은 작업까지 끝난 것은 아닙니다.** 잠든 스레드는 OS에 CPU를 내주지만, 이 풀에서는 아직 사진 처리 함수 안에 머물러 있습니다. 따라서 풀은 그 스레드에게 다음 썸네일 작업을 맡길 수 없습니다. 이 문제의 원인은 계산 능력 부족이 아니라 풀 안의 대기 관계입니다.

**“스레드를 5개로 늘리면요?”** 부모 작업이 네 개뿐인 이 조건에서는 남은 하나가 썸네일을 차례로 처리할 수 있습니다. 썸네일이 끝나면 부모도 깨어나 처리를 마치므로 진행됩니다. 하지만 부모 요청이 다섯 개로 늘어 다섯 스레드를 먼저 차지하면 같은 일이 생길 수 있습니다. 현재 사례의 해결과 재발 방지는 다릅니다.

작업 구조를 바꾸는 한 방법은 사진 처리를 ‘썸네일 요청 전’과 ‘썸네일 완료 후’로 나누는 것입니다. 앞부분은 썸네일을 요청한 뒤 결과를 기다리지 않고 끝나 스레드를 비워 줍니다. 썸네일이 완성되면 뒷부분을 새 작업으로 넣습니다. 그러면 기다리는 동안 작업자 하나를 계속 붙잡지 않습니다. 대신 사진의 중간 결과를 보관하고, 썸네일 실패를 뒷부분에 전달하는 흐름을 설계해야 합니다.

썸네일 전용 풀을 따로 두는 방법도 이 조건에서는 도움이 됩니다. 다만 그 풀의 작업도 다시 원래 풀의 작업을 기다리도록 만들면 두 풀 사이에서 같은 문제가 생길 수 있습니다.

**“시간이 지나면 기다리기를 포기하면요?”** 부모가 실제로 대기를 중단하고 일을 끝내면 스레드는 비게 됩니다. 그러나 사진 처리는 실패한 것이고, 대기열에 남은 썸네일 작업을 어떻게 처리할지도 정해야 합니다. 무한 대기를 끊는 것과 요청을 성공시키는 것은 다릅니다.

</details>

### 22. 다른 변수만 수정하는데 왜 서로의 성능을 떨어뜨릴까요?

서로 다른 물리 코어의 두 스레드가 각자 처리한 사진 수를 세는 전용 카운터, 즉 정수 변수를 반복 갱신합니다. 각 스레드는 자신의 변수만 읽고 쓰며, 같은 변수를 동시에 다루는 데이터 경쟁은 없습니다. 두 변수의 메모리 위치를 가까이 뒀을 때보다 멀리 뒀을 때 실행 시간이 줄었다고 가정합니다. 컴파일러가 반복 갱신을 마지막 한 번의 쓰기로 줄인 상황은 아니며, 처리할 사진 수 등 다른 조건은 같습니다.

CPU 캐시는 메모리를 ‘캐시 라인’이라는 묶음으로 관리하고, 코어 사이의 일관성도 이 단위로 유지한다고 할 때, 가능한 원인과 이를 확인할 비교 실험을 제안해 보세요. 떨어뜨리는 배치가 항상 좋은지도 생각해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 변수는 달라도 같은 캐시 라인에 놓이면 서로의 쓰기가 상대 코어의 캐시 상태에 영향을 줄 수 있습니다. 배치를 바꿔 성능이 개선된 것은 False Sharing을 의심할 단서입니다. 실제 라인 배치와 접근을 확인하고, 다른 조건을 고정한 비교로 가설을 검증하겠습니다.

CPU는 메모리보다 빠르게 값을 읽기 위해 가까운 저장 공간인 캐시에 데이터를 둡니다. 변수 x는 코어 1만, 변수 y는 코어 2만 바꾸더라도 둘이 같은 캐시 라인에 있다면 각 코어가 들고 있는 묶음 안에는 x와 y가 함께 들어갈 수 있습니다.

코어 1이 x를 바꾸면 코어 2가 가진 그 라인의 사본을 예전 상태 그대로 사용할 수 없게 될 수 있습니다. 코어 2가 y를 계속 갱신하려면 해당 라인을 다시 쓰기 위해 코어 사이의 조정이 필요합니다. 변수는 서로 건드리지 않아도 캐시가 관리하는 묶음은 겹치는 것입니다. 각 코어의 반복 쓰기가 해당 라인의 일관성을 유지하는 통신과 재접근을 유발하면, 올바른 결과를 내면서도 느려질 수 있습니다. 이 현상을 **False Sharing(거짓 공유)**이라고 합니다.

같은 라인에 둔 경우와 서로 다른 라인에 둔 경우를 비교하되, 작업량·컴파일 조건·코어 배치 등을 통제하고 반복 측정해야 합니다. 실제 주소와 라인 경계를 확인하고, 지원되는 환경에서는 캐시 간 전송을 관찰하는 도구도 이용할 수 있습니다. 예를 들어 두 실행에서 작업량뿐 아니라 실행 코어 배치도 같게 유지해야 배치 변경의 영향을 비교하기 쉽습니다. 실행 시간이 한 번 줄었다는 사실만으로 원인을 확정하지는 않습니다.

**“모든 변수에 여백을 크게 넣으면 좋을까요?”** 라인을 분리하면 메모리 사용량과 캐시 점유가 늘고, 함께 읽을 데이터가 멀리 떨어져, 한 번에 가까운 데이터를 가져와 재사용하는 이점이 줄어들 수도 있습니다. 자주 갱신하는 데이터에서 효과를 확인해 선택적으로 적용해야 합니다.

**“둘 다 읽기만 한다면요?”** 반복 쓰기에 따른 일관성 유지가 이 가설의 핵심입니다. 읽기만 하는 조건에서도 느리다면 이 설명을 그대로 적용하지 말고 다른 병목을 찾아야 합니다.

</details>

### 23. 메모리를 복제했는데 그 상태를 이어 갈 스레드는 없다면?

Linux에서 하나의 프로세스 안에 스레드 A와 B가 있습니다. A는 공유 목록을 수정하기 위해 뮤텍스 M을 잠갔습니다. 뮤텍스는 같은 잠금을 사용하는 스레드들이 보호된 부분을 한 번에 하나씩 실행하도록 하는 수단입니다. A는 목록 수정을 끝낸 뒤 M을 풀 예정입니다.

그런데 A가 아직 잠금을 가진 동안 B가 fork를 호출해 **새 자식 프로세스**를 만듭니다. 여기서 자식은 21번의 자식 작업과 달리 별도의 프로세스입니다. Linux에서는 다음 두 조건이 함께 성립합니다.

- 자식 프로세스에는 fork를 호출한 B에 해당하는 스레드만 남습니다. A는 복제되지 않습니다.
- 자식 메모리에는 목록과 M의 잠긴 상태도 복제됩니다. M은 프로세스끼리 변경을 공유하도록 설정한 뮤텍스가 아닙니다.

fork 전후에 잠금 상태를 별도로 조정하는 코드는 없다고 가정합니다.

자식에서 기존 작업을 그대로 이어 M을 사용하는 설계에는 어떤 문제가 있을까요? 부모 프로세스에 남은 A가 나중에 M을 풀면 해결되는지, 자식에서 무조건 잠금을 초기화하는 수정은 안전한지도 설명해 보세요.

<details>
<summary>답변과 해설 펼치기</summary>

> 자식은 잠긴 상태를 물려받았지만 그 상태를 정상적으로 풀 A는 물려받지 않았습니다. 부모가 나중에 잠금을 풀어도 사적 메모리의 자식 잠금이 함께 풀리지는 않습니다. 따라서 자식이 기존 멀티스레드 작업을 그대로 이어 갈 수 있다고 가정하면 안 됩니다.

두 프로세스를 나눠 보면 차이가 명확합니다.

| fork 직후 | 부모 프로세스 | 자식 프로세스 |
|---|---|---|
| 남은 스레드 | A와 B | B에 해당하는 스레드만 존재 |
| M의 상태 | A가 잡고 있음 | 잠긴 상태가 복제됨 |
| A가 나중에 잠금을 풀면 | 부모의 M이 바뀜 | 별개 메모리의 M까지 바뀌지는 않음 |

더 큰 문제는 잠금 자체만이 아닙니다. 예를 들어 A가 목록에서 항목을 옮기며 ‘기존 위치에서 제거’까지 하고 ‘새 위치에 추가’하기 전이었다면, 자식에 그 중간 상태가 남을 수 있습니다. 이 예시는 공유 데이터가 여러 단계에 걸쳐 수정될 수 있다는 뜻입니다. 잠금 비트를 억지로 바꾼다고 그 데이터의 일관성이 복구되는 것은 아닙니다. 사용 중인 뮤텍스를 임의로 재초기화하는 방식도 안전한 일반 해법이 아닙니다.

또한 Linux/POSIX에서는 멀티스레드 프로세스의 fork 뒤 자식이 exec까지 호출할 수 있는 함수에 제약이 있습니다. 일반적인 뮤텍스 조작도 이 구간에서 안전한 호출이라고 가정할 수 없습니다. 따라서 여기서는 실행 결과를 하나로 단정하기보다, 잠금 상태는 복제됐는데 그 상태를 마무리할 스레드는 없다는 설계상의 문제를 설명해야 합니다.

새 프로그램을 실행할 목적이라면 자식의 처리를 허용된 최소 작업으로 제한하고 exec로 넘어가는 경로를 설계할 수 있습니다. 기존 작업을 계속할 목적이라면 스레드 시작 전에 작업 프로세스를 만들고 IPC로 일을 전달하는 구조도 검토할 수 있습니다. 예를 들어 먼저 변환용 프로세스를 준비한 다음 메인 서버의 여러 스레드를 시작하고, 변환 요청은 프로세스 간 통신(IPC)으로 전달할 수 있습니다. 그러면 실행 중인 여러 스레드의 잠금 상태를 복제하는 경로를 피하지만, 입력과 결과를 주고받는 규칙을 따로 설계해야 합니다.

**“fork 직전에 내가 만든 락만 모두 정리하면 충분할까요?”** 사용하는 라이브러리의 내부 잠금까지 고려해야 합니다. fork 직전과 직후에 정해 둔 처리를 실행하는 `pthread_atfork` 같은 조정 수단이 있지만 이것 하나로 모든 라이브러리 상태를 자동으로 안전하게 만드는 것은 아닙니다.

</details>
