# 프로세스와 스레드 — 내부 구조를 이해하기

프로세스를 ‘실행 중인 프로그램’이라고 설명할 수 있어도, 그 안에 무엇이 들어 있는지는 별도의 공부가 필요합니다. 실행할 명령어는 어디에 있고, 함수의 지역 변수는 언제 사라지며, 스레드가 늘어나면 무엇이 추가될까요?

여기서는 프로세스의 메모리와 실행 상태를 안쪽에서 살펴봅니다. 구체적인 예시는 C와 Linux/POSIX 환경을 기준으로 합니다. 메모리 배치와 함수 호출의 세부 방식은 운영체제·CPU·컴파일러에 따라 달라질 수 있습니다.

## 1. 프로세스에는 메모리와 실행 상태가 함께 있다

프로그램 파일에는 실행할 명령어와 초기 데이터 등이 들어 있습니다. 이 파일을 실행하면 운영체제는 프로그램이 사용할 메모리와 자원을 준비하고, 명령어를 실행할 흐름을 만듭니다. 같은 프로그램을 두 번 실행해도 각 실행의 진행 위치와 계산 결과는 다를 수 있습니다.

이때 구별할 것이 세 가지입니다.

| 구분 | 담고 있는 것 | 예 |
|---|---|---|
| 주소 공간(Address Space) | 프로그램이 주소로 접근하는 코드와 데이터 | 함수의 명령어, 이미지 배열, 지역 변수 |
| 실행 문맥(Execution Context) | 실행을 이어 가는 데 필요한 현재 상태 | 다음 명령 위치, 스택 위치, 계산 중인 레지스터 값 |
| 운영체제의 관리 정보 | 실행 대상을 관리하고 자원을 찾는 정보 | 식별자, 실행 상태, 메모리 매핑과 열린 파일에 관한 정보 |

레지스터(Register)는 CPU가 현재 계산에 사용하는 작은 저장 공간입니다. 메모리에 이미지가 들어 있다는 것만으로는 이미지 처리의 어느 지점까지 진행했는지 알 수 없습니다. 실행 문맥이 있어야 멈춘 지점에서 이어 갈 수 있습니다.

반대로 CPU를 다른 실행 흐름에 넘겼다고 이미지 배열이 사라지는 것도 아닙니다. **메모리에 데이터가 존재하는 것과 지금 CPU에서 실행되고 있는 것은 다른 상태**입니다. [OSTEP: Processes](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-intro.pdf)

## 2. 프로세스의 메모리 구조를 펼쳐 보기

### 프로그램이 보는 주소는 RAM의 실제 위치와 다르다

프로세스가 사용하는 주소를 가상 주소(Virtual Address)라고 합니다. 운영체제와 하드웨어는 이 주소를 실제 메모리의 위치에 대응시킵니다. 따라서 서로 다른 프로세스가 같은 숫자의 주소를 사용해도 서로 다른 데이터를 가리킬 수 있습니다.

‘프로세스마다 독립적인 주소 공간이 있다’는 설명은 이 관점의 독립성을 뜻합니다. 실제 RAM에 프로세스 하나의 모든 메모리가 한 덩어리로 연속해서 놓인다는 뜻은 아닙니다. 공유 메모리처럼 서로 다른 주소 공간의 일부가 같은 실제 저장 공간을 가리키도록 만들 수도 있습니다. [OSTEP: Address Spaces](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-intro.pdf)

### 코드·데이터·힙·스택은 무엇을 구분하는가

다음은 C 프로그램을 이해할 때 사용하는 대표적인 구분입니다. 실제 주소 순서를 그린 표는 아닙니다.

| 영역 | 주로 담는 내용 | 이해할 때 중요한 점 |
|---|---|---|
| 코드(Text) | CPU가 실행하는 기계어 명령 | 소스 코드의 글자가 그대로 실행되는 것이 아님 |
| 읽기 전용 데이터(Read-only Data) | 문자열 리터럴 등 읽기 전용 데이터 | 실행 중 수정할 일반 변수와 권한을 구분할 수 있음 |
| 초기값 있는 데이터(Data) | 초기값을 가진 전역·정적 변수 등 | 프로그램 시작 때 필요한 초기 내용이 있음 |
| BSS | 0으로 초기화되는 전역·정적 변수 등 | 초기화식을 생략해도 이 변수들은 0으로 시작함 |
| 힙(Heap) | 실행 중 동적으로 확보한 메모리 | 함수 호출이 끝나는 시점과 별개로 수명을 관리함 |
| 스택(Stack) | 함수 호출을 이어 가는 정보와 지역 데이터 | 호출과 반환에 맞춰 사용하는 공간이 달라짐 |

Linux에서 널리 쓰는 실행 파일 형식인 ELF에는 `.text`, `.data`, `.bss` 같은 구획이 있습니다. 특히 `.bss`는 실행 시 0으로 채워질 공간을 나타내므로 실행 파일에 그 크기만큼의 0을 전부 저장할 필요가 없습니다. ‘초기화되지 않은 데이터’라는 이름만 보고 쓰레기 값이 들어 있다고 이해하면 안 됩니다.

이 구분은 학습 모형입니다. 실제 로딩은 여러 구획을 묶은 단위로 이루어질 수 있고, 컴파일러가 변수를 배치하는 방식도 달라집니다. ‘0을 명시한 변수는 반드시 Data’처럼 소스 코드만 보고 최종 위치를 단정하지는 않습니다. [Linux ELF 매뉴얼](https://man7.org/linux/man-pages/man5/elf.5.html)

### 실제 주소 공간에는 더 많은 것이 들어 있다

공유 라이브러리의 코드, 파일을 메모리처럼 접근하도록 연결한 영역, 추가 스레드의 스택도 주소 공간을 구성합니다. Linux의 `/proc/<pid>/maps`에는 이런 주소 구간과 읽기·쓰기·실행 권한 등이 나타납니다. 네 개의 고정된 상자만으로 실제 프로세스 전체를 표현하기는 어렵습니다. [Linux process maps](https://man7.org/linux/man-pages/man5/proc_pid_maps.5.html)

힙은 위로, 스택은 아래로 자라는 그림을 본 적이 있을 것입니다. 이는 제한된 주소 공간을 양쪽에서 사용하는 방식을 설명하기 좋은 모형입니다. 모든 환경의 배치 규칙으로 외우기보다 **용도가 다른 영역이 하나의 주소 공간 안에 있다**는 점을 먼저 이해하면 됩니다. [OSTEP: Address Spaces](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-intro.pdf)

## 3. 변수의 위치와 수명은 어떻게 결정될까

다음 예시는 한 번에 한 스레드만 호출한다고 가정합니다. `sizeof *buffer`는 포인터가 가리키는 정수 한 개의 크기입니다.

```c
#include <stdlib.h>

int limit = 10;
int total;

void record(void)
{
    static int calls;
    int count = 4;
    int *buffer = malloc(count * sizeof *buffer);

    if (buffer == NULL)
        return;

    calls++;
    buffer[0] = calls;
    total += buffer[0];
    free(buffer);
}
```

여기서 `limit`과 `total`은 프로그램 실행 동안 유지되는 전역 변수입니다. `total`은 초기값을 쓰지 않았지만 0으로 시작합니다. `calls`도 같은 기간 유지되지만 이름을 사용할 수 있는 범위는 `record` 함수 안입니다. 따라서 두 번의 할당이 모두 성공했다면 첫 호출에서는 `calls`가 1, 두 번째 호출에서는 2가 됩니다. `total`은 처음의 0에서 1을 더한 뒤 다시 2를 더하므로 3이 됩니다. 반면 `count`는 호출할 때마다 4로 초기화됩니다.

반면 `count`와 `buffer`는 이번 함수 호출에 속한 지역 변수입니다. **이름을 쓸 수 있는 범위(Scope)와 저장 공간이 유지되는 기간(Lifetime)은 별개의 개념**입니다. 함수 안에 선언되었다는 이유만으로 모두 같은 수명을 갖지는 않습니다. 일반 지역 변수의 초기화를 생략했을 때 전역 변수처럼 0을 기대해서도 안 됩니다. [C11 공개 위원회 초안: 6.2.1·6.2.4·6.7.9](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

### 포인터 변수와 할당받은 공간은 서로 다르다

`buffer`에는 정수 배열 자체가 아니라 할당받은 공간의 주소가 저장됩니다. 이를 분리해 보면 다음과 같습니다.

```text
이번 함수 호출의 지역 변수 buffer
              │ 주소를 가지고 있음
              ▼
동적으로 확보한 정수 4개 분량의 공간
```

`free(buffer)`는 아래쪽 공간을 반납합니다. 위쪽 지역 변수의 수명은 함수 반환 때 끝납니다. 함수가 반환된다고 동적으로 할당받은 공간까지 자동으로 반납되는 것은 아닙니다. 반납하지 않은 채 그 공간을 찾을 방법도 잃어버리면 메모리 누수(Memory Leak)가 됩니다.

반대로 공간을 반납한 뒤 그곳을 계속 읽거나 쓰면 해제 후 사용(Use After Free) 문제가 됩니다. 포인터가 있었다는 사실은 대상의 현재 유효성을 보장하지 않습니다. `malloc`으로 받은 공간의 내용 역시 자동으로 0이 되지 않습니다. 위 예시에서는 값을 넣은 `buffer[0]`만 읽습니다. [Linux malloc/free 매뉴얼](https://man7.org/linux/man-pages/man3/malloc.3.html)

설명할 때 지역 변수를 스택에 그리지만, 컴파일러는 지역 값을 레지스터에 두거나 불필요한 저장 자체를 없앨 수 있습니다. C의 변수 수명 규칙과 특정 기계에서의 배치 결과를 구별해야 합니다.

## 4. 스택은 함수 호출을 어떻게 기억할까

`main`이 `read_image`를 호출하고, 그 안에서 `decode`를 호출했다고 해 봅시다. `decode`를 실행하는 동안에도 나중에 `read_image`의 어디로 돌아갈지 알아야 합니다. `read_image`가 끝나면 다시 `main`으로 돌아가야 합니다.

호출마다 필요한 정보를 묶어 스택 프레임(Stack Frame)이라고 부릅니다. 개념적으로는 다음처럼 아직 끝나지 않은 호출이 쌓입니다.

```text
main의 호출 상태          ← read_image가 끝나면 재개
read_image의 호출 상태    ← decode가 끝나면 재개
decode의 호출 상태        ← 현재 실행 중
```

각 호출에는 별도의 지역 상태가 필요합니다. 같은 함수가 자기 자신을 호출하는 재귀에서도 호출마다 서로 다른 지역 값을 유지할 수 있는 이유입니다. 호출이 너무 깊어져 사용할 수 있는 스택 범위를 넘으면 스택 오버플로(Stack Overflow)가 발생할 수 있습니다.

실제 구현에서 인자와 반환 주소가 모두 스택에 들어가는 것은 아닙니다. CPU와 호출 규약에 따라 레지스터도 사용하며, 최적화로 호출 자체가 사라질 수 있습니다. 핵심은 **중단된 바깥 호출을 이어 갈 정보가 필요하다**는 점입니다. [OSTEP: Processes](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-intro.pdf)

함수가 반환된 후 지역 변수의 주소를 계속 사용해도 될까요? 자동 지역 변수의 수명은 이미 끝났습니다. 메모리에 이전 비트가 우연히 남아 있어도 유효한 변수로 사용할 수 없습니다. ‘내용이 지워졌는가’와 ‘사용이 허용되는가’는 다릅니다. [C11 공개 위원회 초안: 6.2.4](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

## 5. 힙을 쓰면 운영체제가 매번 메모리를 주는 걸까

`malloc`은 C 라이브러리의 메모리 할당 함수입니다. 할당기는 확보해 둔 공간을 관리하면서 요청에 맞는 부분을 내어 줄 수 있습니다. 모든 호출을 새로운 운영체제 요청 하나와 동일시하면 안 됩니다.

Linux의 glibc 할당기는 필요에 따라 힙을 늘리거나 `mmap`으로 별도 영역을 확보합니다. `mmap`은 프로세스의 주소 공간에 사용할 영역을 연결하는 기능입니다. 따라서 ‘동적 할당은 모두 하나의 연속된 `[heap]` 구간 안에 있다’는 설명도 실제 구현을 지나치게 단순화한 것입니다. [Linux malloc 매뉴얼](https://man7.org/linux/man-pages/man3/malloc.3.html)

힙과 스택을 비교할 때 중요한 첫 기준은 수명입니다. 함수가 계산 중 잠깐 사용할 작은 값은 호출의 수명과 잘 맞습니다. 반면 이미지 처리 함수가 만든 결과를 함수 반환 후에도 다른 곳에서 사용하려면, 그 결과가 더 오래 살아 있도록 저장 방법을 정해야 합니다. 동적 할당은 그 방법 중 하나입니다.

이때 ‘힙이니까 안전하다’로 끝내면 안 됩니다. 누가 반납할지, 마지막 사용이 언제인지도 정해야 합니다. 함수 경계를 넘어 데이터를 전달할 수 있다는 장점이 수명 관리의 책임과 함께 따라오는 것입니다.

## 6. 스레드가 늘어나면 메모리 구조는 어떻게 달라질까

한 프로세스에 스레드 A와 B가 있으면 둘은 같은 주소 공간 안에서 실행합니다. 하지만 A가 어느 함수를 호출했고 B가 어디까지 계산했는지는 서로 다릅니다. 따라서 각자의 실행 위치, 레지스터 상태, 호출 스택이 필요합니다.

| 함께 사용하는 것 | 실행 흐름마다 필요한 것 |
|---|---|
| 프로세스의 코드와 전역 데이터 | 현재 명령 위치를 나타내는 프로그램 카운터(PC) |
| 동적으로 할당한 메모리를 포함한 주소 공간 | 현재 스택 위치를 나타내는 스택 포인터(SP)와 호출 스택 |
| POSIX 환경의 열린 파일 디스크립터 등 | 계산을 이어 갈 레지스터 상태 |

같은 함수를 두 스레드가 호출해도 함수의 기계어 명령을 두 벌 복사할 필요는 없습니다. 같은 명령을 서로 다른 진행 위치와 지역 상태로 실행할 수 있기 때문입니다. 반면 앞 예시의 `static int calls`는 함수 안에 있어도 스레드별 복사본이 아닙니다. 여러 스레드가 함께 바꾸려면 동기화를 고려해야 합니다. [OSTEP: Threads](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-intro.pdf)

### ‘각자의 스택’이 접근 차단을 뜻하지는 않는다

스택을 따로 가진다는 말은 각 실행 흐름의 함수 호출 상태를 따로 유지한다는 뜻입니다. 같은 주소 공간이므로 한 스레드가 유효한 지역 변수의 주소를 다른 스레드에 전달하면 그 주소로 접근할 수 있습니다.

예를 들어 A의 함수 안에 있는 배열을 B에게 처리하도록 맡긴다면, B의 처리가 끝날 때까지 A의 배열이 살아 있어야 합니다. A가 먼저 반환하면 B는 수명이 끝난 대상을 사용하게 됩니다. 동시에 읽고 쓰는 상황이라면 접근 순서도 조율해야 합니다. 주소를 전달했다는 사실만으로 수명과 동기화 문제가 해결되지는 않습니다. [POSIX threads 개요](https://man7.org/linux/man-pages/man7/pthreads.7.html), [C11 객체 수명 규칙](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

스레드마다 별도의 값을 둘 필요가 있을 때는 스레드 지역 저장소(Thread-Local Storage, TLS)도 사용합니다. 일반 전역 변수의 공유와 구분되는 기능입니다. 또 스레드를 늘리면 스택 등의 자원도 추가로 필요합니다. Linux에서 새 POSIX 스레드의 스택 크기는 생성 속성과 실행 환경의 영향을 받으므로 ‘스레드 하나는 항상 몇 MB’라고 고정해서 외우지 않습니다. [pthreads](https://man7.org/linux/man-pages/man7/pthreads.7.html), [pthread_create](https://man7.org/linux/man-pages/man3/pthread_create.3.html)

## 7. PCB와 문맥 교환은 이 구조의 어디에 있을까

프로세스 제어 블록(PCB)은 운영체제가 프로세스를 관리하는 정보를 설명하는 교과서적 개념입니다. 스레드의 실행 상태를 관리하는 구조는 스레드 제어 블록(TCB)이라고 부릅니다. 실제 운영체제에서는 이 정보가 여러 구조로 나뉘거나 공유될 수 있습니다.

PCB를 ‘프로세스의 모든 메모리를 담는 상자’로 이해하면 혼동이 생깁니다. 이미지 배열의 모든 픽셀을 PCB 안에 넣는 것이 아니라, 운영체제가 메모리와 실행 상태를 관리할 수 있는 정보가 필요합니다. 프로그램의 사용자 영역 변수와 운영체제의 관리 자료는 역할이 다릅니다. [OSTEP: Processes](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-intro.pdf), [OSTEP: Threads](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-intro.pdf)

문맥 교환(Context Switching)에서는 현재 실행을 나중에 재개할 수 있도록 필요한 CPU 상태를 저장하고, 다음 실행의 상태를 복원합니다. 같은 프로세스의 A에서 B로 바뀌면 각자의 명령 위치와 스택 위치 등이 바뀝니다. 프로세스까지 달라지면 주소 공간에 관한 전환도 고려해야 합니다.

이 과정에서 기존 스택과 힙 전체를 매번 다른 곳으로 복사하는 것은 아닙니다. 기존 데이터는 남겨 두고, CPU가 어느 상태로 어느 주소 공간에서 실행할지를 바꿉니다. 다만 다음 실행이 필요로 하는 데이터가 CPU 캐시에 없으면 다시 가져오는 비용 등이 발생할 수 있습니다. 저장하는 레지스터 수만으로 전환 비용 전체를 설명하기 어려운 이유입니다. [OSTEP: Limited Direct Execution](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-mechanisms.pdf)

## 8. 멀티프로세스와 멀티스레드를 구조로 비교하기

두 방식을 고를 때 ‘무거움/가벼움’만 기억하면 데이터와 장애를 어떻게 다룰지 설명하기 어렵습니다. 먼저 경계가 어디에 생기는지 살펴보면 선택의 근거가 드러납니다.

| 관점 | 여러 프로세스 | 한 프로세스의 여러 스레드 |
|---|---|---|
| 주소 공간 | 기본적으로 분리 | 함께 사용 |
| 데이터 전달 | 메시지 전달이나 명시적인 공유 영역 등을 설계 | 같은 객체의 주소로 접근 가능하되 수명·동기화 필요 |
| 잘못된 메모리 접근의 영향 | 다른 주소 공간과의 격리가 보호에 도움 | 같은 프로세스의 다른 작업 데이터까지 손상 가능 |
| 개별 실행의 상태 | 각 실행 흐름의 상태 필요 | 각 실행 흐름의 상태 필요 |

예를 들어 서로 신뢰하기 어려운 확장 기능을 실행한다면 주소 공간의 분리가 중요한 설계 조건이 됩니다. 큰 이미지 배열을 여러 작업이 함께 처리한다면 같은 데이터에 쉽게 접근하는 구조가 유용할 수 있습니다. 어느 쪽이든 CPU 코어 수와 작업 간 의존성이 실제 동시 진행을 제한합니다. 프로세스를 선택했다고 모든 장애가 격리되거나, 스레드를 선택했다고 성능이 항상 좋아지는 것은 아닙니다. [Microsoft: Processes and Threads](https://learn.microsoft.com/en-us/windows/win32/procthread/processes-and-threads), [POSIX threads 개요](https://man7.org/linux/man-pages/man7/pthreads.7.html)

## 스스로 설명해 보기

- 함수 안의 `static` 변수와 일반 지역 변수는 수명이 어떻게 다른가요?
- 지역 포인터로 힙 공간을 가리킬 때, 함수 반환과 `free`는 각각 무엇에 영향을 주나요?
- 스레드마다 스택이 따로 있는데도 다른 스레드의 지역 변수에 접근할 수 있는 이유는 무엇인가요?
- 문맥 교환에서 레지스터를 저장하는 것과 힙을 복사하는 것은 왜 다른 이야기인가요?
